## Missing raw `super`: important, but not missing stock OS content

**A raw `super` dump is not intrinsically required to supply this stock build's five logical firmware images:** those complete image bytes already exist in the validated OTA. AOSP distinguishes full updates from patches and makes successful application conditional on the device being able to receive/apply the package. [AOSP full OTA definition](https://source.android.com/docs/core/ota/tools#build-full-updates).

What is absent is this unit's exact physical `super` container: its logical-partition metadata, extents, both slot layouts, inactive contents, and any allocated COW areas. AOSP documents that `super` contains both layout metadata and logical image contents, and that OTA processing adjusts the target metadata. **Inference:** a correctly supported full-OTA installation can reconstruct its intended target firmware without an exact old `super` image; saving the extracted images alone does not implement that process or establish a safe hand-built replacement layout. No factory `super.img` is present in this package. [Local validation](stock-firmware-validation-2026-11-11.json), [AOSP dynamic partitions and factory images](https://source.android.com/docs/core/ota/dynamic_partitions/implement).

Saved `metadata` inspection and the later fastbootd query both indicate no pending snapshot update. That reduces the previously identified concern about omitted userdata-backed firmware snapshots, but cannot validate uncaptured `super` bytes or layouts. [Scope analysis](recovery-backup-scope-review.md), [saved fastbootd query](../.private/fastbootd-bootloop-query-2026-11-11.json).

## Is there a documented non-EDL, non-root backup route now?

**None established for these missing partitions under the stated constraints.** The exact saved B recovery identifies Android 11. The inspected [local AOSP Android 11 command source](../.local/firmware-tools/fastboot-device-commands-android11.cpp) has no fetch handler. AOSP documents that `fetch` was added in Android 12, with checks requiring a debuggable, unlocked build and the `vendor_boot` partition. This is not a documented general `super`/configuration dump facility, and upgrading the Mac's fastboot client cannot add device support. BOOX-specific extensions remain unknown; do not infer that every OEM read method is impossible. [Saved recovery builds](../.private/recovery-backup-20261111-095553/recovery-slot-builds.json), [AOSP fastbootd fetch requirements](https://source.android.com/docs/core/architecture/bootloader/fastbootd#fastbootd-changes).

Normal Android's saved shell runs as UID 2000; the recorded boot and `super` block devices are root-only (`0600`). Therefore ordinary file pulling or a shell copy is not an established way to read those raw partitions without additional privilege. No rooting, booting a new recovery, flashing, or undocumented OEM command is proposed. [Saved identity and access checks](device-inventory-2026-11-11.json).
