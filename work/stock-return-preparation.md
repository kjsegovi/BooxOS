# Stock-return preparation — GoColor7_2 — 2026-11-11

**Decision: stock return is not yet demonstrated, and this kit is not sufficient evidence to begin LineageOS installation.** Offline analysis substantially improves the proposed return route: the preserved November 2025 **B recovery** is a better full-OTA candidate than April 2026 **A recovery**, because A contains a timestamp that is 683 seconds newer than the matched OTA. Both recoveries contain the same update binaries and the same package-matching update certificate. B avoids that particular comparison on its saved properties; it has **not** accepted, applied, or booted this OTA in a test.

This work opened saved local files and primary documentation only. It performed **no USB/device query, reboot, slot change, flag change, EDL entry, flash, erase, recovery installation, or reset**. The working original April build on successful/bootable A remains the last observed device state. [Current status](recovery-backup-status.md), [saved follow-up](boot-status-check-2026-11-11.json).

## What the existing evidence proves

The matched manufacturer download was decrypted without altering its contents. Prior checks establish HTTPS origin, published digest, exact model/build, ZIP integrity, whole-package and payload signatures under the copied installed update certificate, and complete reconstruction of 13 payload images. Those are independent of recovery acceptance. The key is the common `testkey.x509.pem`; it is not proof of exclusive manufacturer authorship. The manufacturer `update.upx` and its decrypted signed `update.zip` are distinct delivery formats; do not pass the encrypted UPX to an AOSP ZIP sideload interface merely because the stock Settings updater uses UPX. [Validation](stock-firmware-validation-2026-11-11.json), [BOOX's documented local-update route](https://booxsupport.zendesk.com/hc/en-us/articles/360027768511-How-to-update-to-the-latest-firmware-on-my-BOOX-device).

New offline checks independently rehashed all 13 extracted images against the payload, revalidated both saved GPT header/entry-array CRCs, and checked physical image sizes against both A/B GPT capacities. They also extracted both captured recovery ramdisks directly from the hash-verified recovery images, compared their trust certificates and update binaries, inspected raw protobuf fields omitted by the older extractor, and verified the AVB graph. [Machine-readable results](../.local/stock-return-analysis/offline-stock-return-analysis.json), [binary inspection](../.local/stock-return-analysis/binary-inspection.json).

The 31 own-device raw captures remain a partial backup. In particular, no exact raw `super` metadata/extents are saved; many firmware/security/configuration partitions, eMMC auxiliary areas and RPMB are absent. The Downloads kit is a verified second folder on the same Mac, not a separate-device backup. The old `misc`, `metadata`, and GPT images are evidence and possible specialist recovery material, **not automatic replay inputs**. [Coverage review](recovery-kit-gap-review.md), [copy verification](recovery-kit-downloads-copy-2026-11-11.json).

## Acceptance checks, including the timestamp trap

The OTA has `ota-type=AB`, `pre-device=GoColor7_2`, `post-timestamp=1776750860`, payload major version 2/minor 0, and no `pre-build`, `pre-build-incremental`, serial restriction, or `ota-downgrade=yes`. All 13 partitions lack `old_partition_info`; operations are only complete replacement/zero forms, and all `run_postinstall` flags are false. This is a full payload, so source-build block hashes are not required to reconstruct its image content. Receiving and applying the package must still work. [Local parsed facts](../.local/stock-return-analysis/offline-stock-return-analysis.json), [AOSP full-update definition](https://source.android.com/docs/core/ota/tools#build-full-updates).

| Execution environment | Saved relevant timestamp | Comparison with OTA `1776750860` | What follows |
| --- | ---: | --- | --- |
| Normal April Android, system properties | `1776750860` | Equal | No global same-build timestamp rejection predicted from the saved values. This does not test the BOOX app or updater. |
| April A recovery ramdisk, Android 11 / incremental 8525 | `1776751543` | OTA is 683 seconds older | AOSP-compatible recovery and sideload updater predict rejection unless BOOX changes the runtime property or policy. |
| November B recovery ramdisk, Android 11 / incremental 6191 | `1762762904` | OTA is 13,987,956 seconds newer | Passes this comparison only; strongest preserved recovery candidate for further qualification. |

These are **different execution environments**. AOSP Android 11 recovery checks the running recovery's `ro.build.date.utc` against ZIP `post-timestamp`; an older package requires the downgrade flag and a nonempty source fingerprint. It also checks A/B type, exact product, optional serial restriction, and any optional source-build restrictions. The signed package cannot be edited to add downgrade metadata without invalidating its signature. [Pinned recovery implementation, `CheckPackageMetadata` / `CheckAbSpecificMetadata`](https://android.googlesource.com/platform/bootable/recovery/+/1ed404b31fa668bdb6569fc7ba4e8009a0938ee6/install/install.cpp#142).

There is a second, independent gate: Android 11 `update_engine_sideload` compares payload `max_timestamp` with `HardwareAndroid::GetBuildTimestamp()`, which reads `ro.build.date.utc`. The standard downgrade exception requires **both** `ro.ota.allow_downgrade` and `ro.debuggable`; these production ramdisks have `ro.debuggable=0` and no allow-downgrade property. Unlock state alone does not remove this gate. [Pinned manifest validation](https://android.googlesource.com/platform/system/update_engine/+/becedca931b88b070d70b6e7bead3b6dfd82ff96/payload_consumer/delta_performer.cc#1774), [pinned property/downgrade implementation](https://android.googlesource.com/platform/system/update_engine/+/becedca931b88b070d70b6e7bead3b6dfd82ff96/hardware_android.cc#191).

This is not merely a source-level hypothetical. The two saved recoveries contain byte-identical `recovery` binaries and byte-identical `update_engine_sideload` binaries. Both contain the relevant property names and failure paths. Their embedded debug symbol data allowed static inspection of the timestamp comparison and downgrade branches in the **actual binaries**. That supports the A/B prediction; it is not a complete control-flow audit or runtime test. Android 11 initialization can load several property files, so the eventual recovery runtime values still need to be established instead of assuming that ramdisk values are necessarily final. [Exact-binary evidence and disassembly pointers](../.local/stock-return-analysis/binary-inspection.json), [AOSP property loading](https://android.googlesource.com/platform/system/core/+/a790490ec973cd1799384a367da59d0200591c0a/init/property_service.cpp#876).

The old local protobuf reader did not expose partition version field 17. A raw-wire check now finds `odm` and `vendor` version **1776751543**, and `system`, `product`, `system_ext` version **1776750860**; boot/recovery have no version field. No partial-update field 16 is present. Android 13 update_engine checks the global timestamp for full updates and then available per-partition versions. Thus the normal stock Android values being equal to their corresponding payload values explains why the cross-partition 683-second difference is not intrinsically a normal-Android downgrade. A future newer Lineage build may fail these checks, and its updater cannot be assumed to behave like BOOX's. [Android 13 check](https://android.googlesource.com/platform/system/update_engine/+/2fafacaedef0f4b01a357c17bb48a701d66b8eef/payload_consumer/delta_performer.cc#982), [partition-property mapping](https://android.googlesource.com/platform/system/update_engine/+/2fafacaedef0f4b01a357c17bb48a701d66b8eef/aosp/hardware_android.cc#308), [version field definition](https://android.googlesource.com/platform/system/update_engine/+/2fafacaedef0f4b01a357c17bb48a701d66b8eef/update_metadata.proto#306).

### Trust matching is necessary, not acceptance

Neither saved recovery has `/res/keys`. Both contain `/system/etc/security/otacerts.zip`, with a certificate whose DER SHA-256 is `d15235d239fad4d6731e72c409660b07957824fda0be7e91299ecca298eebf55`, exactly matching the OTA's certificate and previously copied normal-system certificate. This closes the **recovery trust-file mismatch** question offline. AOSP Android 11 recovery loads this certificate ZIP for whole-package verification before invoking `update_engine_sideload`; the actual binaries also contain that path. It does not close timestamp, layout, privilege, rollback, slot, or boot-success questions. [Offline A/B certificate results](../.local/stock-return-analysis/offline-stock-return-analysis.json), [pinned recovery trust and invocation source](https://android.googlesource.com/platform/bootable/recovery/+/1ed404b31fa668bdb6569fc7ba4e8009a0938ee6/install/install.cpp#634).

## Restoration paths and their present status

| Route | Evidence for it | Remaining boundary |
| --- | --- | --- |
| BOOX Settings local update using the untouched exact-model `update.upx` | Official BOOX documentation describes this route on working stock Android. | Reinstallation of this same version is untested, and it depends on working BOOX software. It is not a demonstrated return route from LineageOS. |
| Stock recovery full A/B OTA using the decrypted **signed ZIP** | Both stock images contain recovery, sideload and updater components; trust matches; full payload has no source-block dependencies. B is the timestamp-compatible candidate. | Neither A nor B has been observed accepting/installing this ZIP. Exact entry/routing, runtime properties, storage/layout handling and completion need qualification. No official exact-model recovery-sideload procedure was established by this research. |
| Userspace fastboot (`fastbootd`) restoring matched images | This reader previously exposed userspace fastboot and allowed an explicitly approved slot selection; AOSP has logical-partition flashing handlers. | **No firmware write was tested.** Per-partition access, size/layout reconstruction, download limits, sparse/raw support, AVB and reset/slot order are not established. Generic AOSP support is not BOOX-specific approval. |
| EDL raw restoration | Partial own-device images/GPT exist. | Held after the failed read incident. No EDL write/restore is qualified or proposed. Missing raw assets prevent a complete disk replay. |

BOOX's documented cloud/local update procedure is the only manufacturer-supported update path established here; its exact-model warning is explicit. AOSP documents fastbootd because bootloader fastboot cannot generally interpret logical partitions inside `super`. Its Android 11 handlers reject flashing while locked and protect partitions during a snapshot update; a working query/slot command does not prove a working write handler or policy for every partition. [BOOX procedure](https://booxsupport.zendesk.com/hc/en-us/articles/360027768511-How-to-update-to-the-latest-firmware-on-my-BOOX-device), [dynamic-partition architecture](https://source.android.com/docs/core/ota/dynamic_partitions/implement#fastbootd), [pinned flash handler](https://android.googlesource.com/platform/system/core/+/a790490ec973cd1799384a367da59d0200591c0a/fastboot/device/commands.cpp#521).

**Do not equate full-OTA recovery sideload with guaranteed preservation of the other slot.** The pinned Android 11 Virtual A/B implementation can fall back, after snapshot preparation fails in recovery, to deleting source logical groups and overwriting existing logical content; its own diagnostic says the source may be unbootable until the update finishes. The exact stock updater contains the corresponding source-deletion function. Both recoveries advertising A/B does not provide two independent complete stock systems: logical firmware lives in shared `super`. There is no established non-writing sideload “acceptance test”; once accepted, updater execution can write firmware. [Pinned fallback and source-deletion implementation](https://android.googlesource.com/platform/system/update_engine/+/becedca931b88b070d70b6e7bead3b6dfd82ff96/dynamic_partition_control_android.cc#393), [actual binary function evidence](../.local/stock-return-analysis/binary-inspection.json), [Virtual A/B architecture](https://source.android.com/docs/core/ota/virtual_ab).

### Layout requirements

The payload names one update group, `qti_dynamic_partitions`, maximum **6,438,256,640 bytes**, containing the five logical images, totaling **4,841,910,272 bytes**. Saved GPT `super` is **6,442,450,944 bytes**; the difference between container and group maximum is 4,194,304 bytes. Dynamic metadata enables snapshots; no compressed-snapshot fields are present. These facts are consistent with the saved Virtual A/B configuration. They are **not** an exact `lpmake` recipe: geometry, metadata slots, extents, alignment, device flags, source/target metadata and any later Lineage layout remain unobserved. [Parsed payload/GPT](../.local/stock-return-analysis/offline-stock-return-analysis.json), [AOSP layout and group constraints](https://source.android.com/docs/core/ota/dynamic_partitions/implement).

The inspected stock updater has a Virtual A/B exception before halving allocatable space, unlike the unmodified early Android 11 source branch used for comparison. Static symbols and its function-pointer table identify that extra check. Therefore do not incorrectly require these five images to fit in **half** of this 6.44 GB `super`, or claim that generic source alone proves rejection. Actual writable logical metadata and allocation still must be proven. [Exact-binary space check](../.local/stock-return-analysis/binary-inspection.json).

No factory `super.img`, `super_empty.img`, fastboot `android-info.txt` package or OEM raw-programming manifest was found in this OTA. A signed A/B OTA is not a `fastboot update` factory-image archive. Do not concatenate the five images, use an arbitrary generic `super` layout, or treat Android 12+ `vendor_boot` examples as this device's separate Android 11/header-v2 boot/recovery scheme. [Package entries](stock-firmware-validation-2026-11-11.json), [AOSP factory `super.img` distinction](https://source.android.com/docs/core/ota/dynamic_partitions/implement#factory-images).

### AVB requirements

Offline upstream `avbtool` verification passed the top-level and chained VBMeta signatures; boot/recovery/dtbo hashes; and odm/vendor/product/system/system_ext hashtrees. The actual child public key equals the parent's `vbmeta_system` chain descriptor, and the chain descriptor's rollback-index location is **2**. `vbmeta` has rollback index **0**, `vbmeta_system` **1775001600**, and both have flags **0**. Their graph is:

- `vbmeta` → hashes for **boot, recovery, dtbo**; hashtrees for **odm, vendor**; chain to **vbmeta_system**.
- `vbmeta_system` → hashtrees for **system, system_ext, product**.

These are a matched stock set. Restore planning must keep those relationships consistent within the intended slot, including original verification flags. This check uses embedded keys and does not establish the bootloader's root of trust or hardware-stored rollback counters. The verifier also explicitly does not verify FEC parity. A future custom OS that advances stored rollback state may make these older stock images unusable under enforced verification. **Relocking is not part of the proposed return route.** [Verification transcript](../.local/stock-return-analysis/avb-verify.txt), [top-level metadata](../.local/stock-return-analysis/avb-info-vbmeta.txt), [system metadata](../.local/stock-return-analysis/avb-info-vbmeta_system.txt), [pinned AVB trust/rollback design](https://android.googlesource.com/platform/external/avb/+/08d4586def763729be5916fce33ac41c50874062/README.md#rollback-protection).

## What must be established before LineageOS installation

1. **Exact bounded installation scope.** List every partition/state change the contemplated Lineage method performs, including recoveries, boot images, AVB flags/keys/rollback indexes, logical groups, snapshots, firmware and any data reset. Every changed area needs a return asset and a usable return path. Preserve B's original recovery as a candidate; do not assume a slot label protects its logical OS content.
2. **A usable path when Android cannot boot.** The stock B recovery/fastbootd menu was reached during the incident, but future entry must remain possible after the exact planned changes. A later separately authorized qualification should establish mode identity, recovery build/runtime properties, model, slot, lock and snapshot state, then return to working A without selecting an update. Choosing B or changing boot metadata is a device mutation requiring its own concrete reviewed operation; none is performed here.
3. **Resolve the recovery acceptance question.** Obtain exact-model manufacturer guidance/package support or a sufficiently controlled qualification of the unmodified signed full OTA through the intended recovery. B is a candidate because its timestamp is older and its binaries/key match. This requires installation authorization if an update is started; signature checking or a sideload progress bar is not a successful restoration. Do not “try A first” on the assumption that signatures imply acceptance.
4. **An exact layout/snapshot/slot plan.** Establish the current source/target logical metadata, required free allocation, no pending merge, handler access and preservation/reconstruction rules. Recovery's full-OTA fallback may overwrite source logical groups. Fastbootd fallback requires an independently justified metadata plan and confirmed write capability; the table above alone does not supply either.
5. **Coherent AVB and rollback behavior.** Keep the stock graph/flags and paired images intact; establish that the planned custom build cannot make stock rollback values unusable. Do not rely on the current unlocked/orange state as an assurance after arbitrary firmware or relocking changes.
6. **A clean-data return policy.** The user's omitted-userdata choice permits a clean stock return, not replay of stale encryption/snapshot state. Use the chosen supported reset path only after coherent firmware is established. Do not restore saved `metadata` over new `userdata`, wipe metadata alone, or assume a factory reset recreates firmware/calibration/security partitions. BOOX documents that factory reset formats storage. [BOOX reset/data warning](https://booxsupport.zendesk.com/hc/en-us/articles/8569527734932-Firmware-Updates).
7. **Completion evidence.** A real qualification must capture installer completion, original April build/model/slot, a successful/bootable target slot, no pending snapshot work, completed boot, and a normal restart. User checks should confirm display/color/refresh, touch/buttons, Wi-Fi/audio and required BOOX reading/stylus functions. The saved November 11 boot-status pass proves the present recovered A only, not this unperformed restore.

If those gates cannot be closed without sacrificing the only working installation and no reliable alternative recovery is established, the correct result remains **no LineageOS installation**. Filling backup gaps or bypassing timestamp checks by editing signed metadata is not a substitute for a tested return path.

## Reproducible offline outputs

The analysis scripts are confined to `.local/stock-return-analysis/`; their reads are saved local files and their writes are local analysis outputs. They contain no ADB, fastboot, EDL, block-device or flash/erase operations. They do not modify protected kit assets.

- [`analyze_stock_return.py`](../.local/stock-return-analysis/analyze_stock_return.py): completed successfully; revalidates saved GPT CRCs, both recovery-image hashes/certificates/properties, all 13 payload-image hashes and physical capacities, raw partition-version fields, AVB chain-key equality, signatures/hash/hashtrees. Output: [`offline-stock-return-analysis.json`](../.local/stock-return-analysis/offline-stock-return-analysis.json). The AVB tool returns **0** with an explicit expected child key and rollback location.
- [`inspect_binaries.py`](../.local/stock-return-analysis/inspect_binaries.py): completed successfully; verifies selected binary hashes, extracts their embedded `.gnu_debugdata`, identifies named functions, and generates disassembly for review. Output: [`binary-inspection.json`](../.local/stock-return-analysis/binary-inspection.json). Static interpretation is labeled separately from runtime proof.
- [`aosp/source-manifest.json`](../.local/stock-return-analysis/aosp/source-manifest.json): exact immutable upstream source URLs, commits, lengths and SHA-256 values, including the unmodified upstream Python 3 AVB verifier used for checks. Downloading those public files is the only network activity of the scripts; `fetch_sources.py` is separate from the offline analyses.
