# Stock debug ramdisk as a backup route — 2026-11-11

**Finding: this is a technically plausible non-EDL backup avenue, but it is not ready for a device trial or a usable debug-boot artifact.** The exact stock first-stage `init` implements the official debug-ramdisk mechanism, and the exact stock Android 13 ADB daemon retains a runtime root path. However, a two-file `/force_debuggable` + `/adb_debug.prop` edit is insufficient for this Android 11 first stage: it also requires a compatible debug platform SELinux policy. No such policy ships in the matched system/system_ext images, and the ordinary stock policy does not contain the explicit ADB-to-`su` debug transition. Native bootloader RAM boot is also unverified.

**GO:** continue offline policy/compiler and artifact-design preparation while preserving stock kernel, DTB, DTBO, vendor, firmware and original boot assets. **NO-GO:** call a properties-only image usable, boot modified code, flash a boot partition as an automatic fallback, or claim a validated raw backup route. No boot artifact was created or patched for this research. No USB/device action occurred.

The first-stage binary's embedded debug symbols identify `FirstStageMain` at **0x25d4f0**. Disassembly shows the `/force_debuggable` existence test at **0x25e38c**, property and policy copy calls at **0x25e3f4** and **0x25e444**, and `INIT_FORCE_DEBUGGABLE=true` setup at **0x25e6a0–0x25e6b4** only after success. This matches the official Android 11 mechanism: both copied files are required before the environment flag is set. Adding only a marker and properties cannot satisfy that code. [Exact-binary report/disassembly](../.local/stock-return-analysis/debug-ramdisk/debug-route-analysis.json), [pinned first-stage source](https://android.googlesource.com/platform/system/core/+/a790490ec973cd1799384a367da59d0200591c0a/init/first_stage_init.cpp#289).

Official AOSP documentation describes debug ramdisks for unlocked devices using user-build systems, including OEM systems. It describes loading a **userdebug platform policy**, not merely setting a property. This establishes a supported Android engineering mechanism; it is not a BOOX-supplied debug image or exact-model compatibility guarantee. [AOSP overview](https://source.android.com/docs/core/tests/vts/vts-on-gsi).

## The root gate is runtime, not an established permanent compile-time prohibition

The exact normal-Android adbd includes `restart_root_service` at **0xb1fa0**. At **0xb1fd0** it calls `__android_log_is_debuggable`; the false branch returns the production-build refusal, while the true path sets `service.adb.root=1`. Its `adbd_main` at **0x9b088** includes runtime `ro.secure`, debug status and `service.adb.root` decisions, a conditional drop to UID/GID 2000, and the alternative root-path `selinux_android_setcon` call at **0x9b544**. Root has **not** been compiled away in this saved binary. [Binary evidence](../.local/stock-return-analysis/debug-ramdisk/debug-route-analysis.json), [pinned restart implementation](https://android.googlesource.com/platform/packages/modules/adb/+/ef7818f751655cfa9aa36e824f13289b336079e0/daemon/restart_service.cpp#31), [pinned daemon privilege logic](https://android.googlesource.com/platform/packages/modules/adb/+/ef7818f751655cfa9aa36e824f13289b336079e0/daemon/main.cpp#66).

Therefore the present production-root refusal would not establish that a debug ramdisk can never work. Conversely, the presence of the root branch does not prove that the necessary properties load, the root restart succeeds, the SELinux transition is allowed, or raw partition reads succeed. These remain separate gates.

Android 13 second-stage init retains the debug ramdisk only when the first-stage environment flag is true **and** AVB reports unlocked; otherwise it unmounts it before loading properties. Debug properties are loaded after ordinary partition properties, allowing the intentional read-only-property override. The saved device was unlocked/orange, but a future session must not assume that state is unchanged. [Second-stage gate](https://android.googlesource.com/platform/system/core/+/83366e7e7a1556ab6cff117673bb9f17b973de99/init/init.cpp#873), [property precedence](https://android.googlesource.com/platform/system/core/+/83366e7e7a1556ab6cff117673bb9f17b973de99/init/property_service.cpp#1122).

## Authentication and proposed property contract

For a future reviewed candidate, the property contract should be:

```properties
ro.debuggable=1
ro.force.debuggable=1
ro.adb.secure=1
ro.secure=1
```

Keep authentication enabled; keep privilege dropping by default; require a separate, explicit root restart after an authenticated connection. Do not pre-set `service.adb.root`, add TCP/wireless debugging properties, or copy AOSP's test-automation default `ro.adb.secure=0`. That default deliberately disables authorization; it is not needed for this backup objective. [AOSP test property file](https://android.googlesource.com/platform/system/core/+/a790490ec973cd1799384a367da59d0200591c0a/rootdir/adb_debug.prop), [normal adbd authorization selection](https://android.googlesource.com/platform/packages/modules/adb/+/ef7818f751655cfa9aa36e824f13289b336079e0/daemon/main.cpp#210).

The exact daemon contains the secure-auth property path, and the extracted system `libadbd_auth.so` contains both `/adb_keys` and `/data/misc/adb/adb_keys`. Official implementation reads authorized **public** keys from those locations and performs the normal ADB challenge/response. The workstation's private ADB key belongs on the workstation only; never put it into a boot image, backup kit, report or device. Prefer existing stock-Android host authorization; if using a new Linux ADB identity, ordinary on-device authorization while stock Android works is a separate user-visible prerequisite. [Pinned key iteration](https://android.googlesource.com/platform/frameworks/native/+/2fe7eddf185ecb63223eeadc58804f9bf6cbd426/libs/adbd_auth/adbd_auth.cpp#391), [saved binary strings/hashes](../.local/stock-return-analysis/debug-ramdisk/debug-route-analysis.json).

Do not assume that adding `/adb_keys` to the first-stage ramdisk makes it visible after switching to the system root. This debug mechanism explicitly preserves the debug properties and policy, not arbitrary files. No host key was read or embedded in this investigation. If data cannot mount or the host is unauthorized, stop; do not silently disable authentication to obtain access.

## SELinux is the main offline engineering gap

The stock ADB service asks a root daemon to transition from `adbd` to `su`. Official policy places `adbd`'s `setcurrent`/`su dyntransition` allowances and the permissive `su` domain inside `userdebug_or_eng`. The saved platform CIL lacks the explicit debug forms. UID 0 alone does not bypass SELinux, and a failed `setcon` is fatal in adbd. A valid root shell also needs permission for the actual block-device labels and required read/seek/query operations. [Pinned ADB policy](https://android.googlesource.com/platform/system/sepolicy/+/6f6029407a5e7059e2ae2ac2e6cfd0c9b4e00509/private/adbd.te#8), [pinned `su` policy](https://android.googlesource.com/platform/system/sepolicy/+/6f6029407a5e7059e2ae2ac2e6cfd0c9b4e00509/private/su.te).

This hybrid needs a policy compatible with the **actual Android 13 platform policy and its OEM additions**, combined with the saved vendor/odm/system_ext/product policies and API mappings. A generic Android 11 userdebug CIL is not an adequate substitution simply because first-stage init came from Android 11. Android 13 init compiles the selected debug platform policy with the other partition policies and deliberately bypasses the vendor precompiled policy when a debug platform policy is selected. A policy compiler failure can prevent boot. [Pinned policy selection/compilation](https://android.googlesource.com/platform/system/core/+/83366e7e7a1556ab6cff117673bb9f17b973de99/init/selinux.cpp#308).

**Prepared:** all **70** SELinux inputs from the five matched OS images were extracted offline, totaling **5,895,350 bytes**, with a per-file hash manifest. This includes platform CIL, mappings, OEM partition policy and existing precompiled-policy material. [Policy manifest](../.local/stock-return-analysis/debug-ramdisk/policy-inputs/manifest.json). **Not done:** combined-policy compilation, a compatible debug policy, or validation of exact effective raw-read permissions.

The next useful offline milestone is to compile the untouched saved policy inputs with a matching host compiler as a baseline, then produce and inspect a narrowly justified debug variant. Prefer an enforcing, bounded read-access design if feasible. Do not substitute global permissive mode or treat AOSP's broad test `su` permissions as inherently read-only. No policy file was patched here.

## Boot format and AVB constraints

The current boot image is 100,663,296 bytes. Its AVB footer describes **62,304,256 bytes** of original boot content and an embedded **Algorithm NONE** VBMeta block. The authenticated stock `vbmeta` separately contains the SHA-256 descriptor for that boot content. Editing the ramdisk invalidates that parent descriptor even if the kernel and DTB are unchanged; retaining an old footer does not preserve validity. Adding a test-key footer also does not make it match the manufacturer-signed parent. [Exact boot AVB output](../.local/stock-return-analysis/debug-ramdisk/stock-boot-avb-info.txt), [stock graph](stock-return-preparation.md).

A future local candidate would need correct boot-v2 header fields/ID, ramdisk compression and page alignment, unchanged kernel/DTB bytes, preserved addresses/cmdline/DTB information, and internally consistent rebuilt footer metadata. No replacement of `vbmeta`, disabling verification flags, relocking, or bootloader-firmware change belongs in this RAM-boot proposal. Whether this unlocked BOOX permits a modified RAM boot despite its changed hash is unverified. An unmodified stock RAM-boot success would establish the command/transport path, **not** modified-image AVB acceptance. AOSP's debug-image instructions allow non-release keys only under the unlocked-device assumption. [AOSP debug-image AVB requirements](https://source.android.com/docs/core/tests/vts/vts-on-gsi#add-an-avb-footer).

The saved boot-header command line contains `buildvariant=user` and no `skip_initramfs` or `androidboot.force_normal_boot=1`; the ramdisk has no `first_stage_ramdisk` subtree. Bootloaders can append command-line values, so future path placement must use the effective configuration rather than add both root paths blindly. The Android 11 implementation switches root before looking for the marker when force-normal-boot is in use. [First-stage path handling](https://android.googlesource.com/platform/system/core/+/a790490ec973cd1799384a367da59d0200591c0a/init/first_stage_init.cpp#278).

## Required ordering before any future trial

1. **Finish offline policy validation first.** Keep the candidate manifest limited to the debug files/policy changes and structural repacking; independently demonstrate unchanged kernel, DTB, DTBO and every original ramdisk entry that is not intentionally changed. No modified image currently exists.
2. **Qualify native RAM boot using untouched stock first, if separately authorized.** Userspace fastbootd connectivity does not establish native bootloader `boot` support. The first-generation report of “unknown command” is a warning, not proof for this unit. Confirm a concrete native-mode entry/exit route and explicit current slot before attempting the stock-only RAM path. Do not issue a slot change or partition write to make this test possible by default. [Official fastboot protocol distinction](https://android.googlesource.com/platform/system/core/+/a790490ec973cd1799384a367da59d0200591c0a/fastboot/README.md).
3. **Stop if RAM boot is unsupported.** Flashing a physical boot partition is a materially different, persistent experiment requiring the user's explicit approval and a concrete recovery plan. It is outside the current offline scope and must not be an automatic fallback.
4. **Only then consider an authenticated modified RAM trial.** It would need its own approval, hashed candidate, policy proof, expected USB/root/SELinux observations, timeout and exact return-to-original plan. Stock RAM-boot success does not authorize modified execution.
5. **Qualify small reads before a long backup.** Prove authenticated UID 0, expected SELinux context/enforcing state and named raw-read access. Compare bounded repeated reads with saved originals; stream to the Linux host, avoiding on-device backup files. Observe snapshot/update state and stop on unexpected state rather than cancelling an update or clearing metadata.
6. **Require coherence and return evidence.** Firmware partitions may be quiet while normal Android runs, but Android still writes data/configuration/logs and can perform update work. Define a stable capture scope, repeated critical checks and hashes, excluded personal storage, sufficient host capacity and a protected second copy. Finish by returning to original stock A and checking completed boot, slot success and a normal restart.

The fastboot `boot` operation downloads and executes an image in memory rather than programming a named partition. **That does not make the resulting Android session storage-read-only.** A stock or debug Android boot can change persistent runtime state, and even successful raw reads do not prove a future raw restoration write path. The resulting backup would improve recovery coverage without qualifying Lineage installation by itself.
