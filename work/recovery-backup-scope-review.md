# Firmware-only recovery backup scope review

Reviewed **2026-11-11**, for this **GoColor7_2 / SM6350**, Android 13 system with Android 11 vendor. Research and saved evidence only: no USB/device access, mode change, firmware write, or tool modification was performed in this review.

## Recommendation

**Proceed with a smaller, private recovery-asset backup, but do not describe it as a complete, restore-ready checkpoint while snapshot dependencies remain unresolved.** Omitting `userdata` is compatible with a recovery goal that accepts a factory reset. It is not automatically compatible with restoring the currently running firmware from raw `super` and `metadata` alone.

The practical minimum proposed here is **all 76 named LUN0 partitions except `userdata`, `rawdump`, `logdump`, and `logfs`, plus both GPTs and protective MBR**, retaining the matched full OTA and its verification record. These partition payloads total **8,056,108,032 bytes (8.056 GB / 7.503 GiB)**; the already saved GPT/MBR files total **22,016 bytes**. `rawdump`, `logdump`, and `logfs` are excluded on their apparent diagnostic role, not on an OEM-proven content classification. Capturing all 79 non-`userdata` partitions instead adds 209,715,200 bytes, but could preserve crash/log contents unrelated to firmware recovery. Size calculations come directly from the [saved inventory](../.private/backup-access-real-storage-20261111-094142/partition-inventory.json).

Preserve both physical slot sets, complete raw `super` (6 GiB), `metadata` (16 MiB), `misc`, and all retained configuration/security/manufacturer partitions, including `xbl_config_a/b`, `persist`, `onyxconfig`, `devinfo`, `frp`, `keystore`, `modemst1/2`, `fsg` and `fsc`. No complete OEM unique-state map is available to justify trimming these small unknown areas. Keeping `misc` is prudent because AOSP permits persistent snapshot merge status there. This is an engineering preservation choice, not proof of each BOOX partition's contents. [AOSP Virtual A/B implementation](https://source.android.com/docs/core/ota/virtual_ab/implement#boot-control-hal).

## Factory reset: what it can and cannot repair

**Conditional answer: yes, firmware recovery without old personal data is possible in principle, provided a complete bootable firmware state is restored or reconstructed first.** AOSP recovery checks/completes pending snapshot work before formatting `/data` and, when present, `/metadata`; it refuses the wipe when that snapshot step fails. Reset initializes the data environment. It does not reinstall missing operating-system blocks or rebuild arbitrary damaged bootloader/calibration partitions. BOOX's actual reset implementation and successful recovery on this unit have not been demonstrated. [AOSP recovery `WipeData` reference](https://android.googlesource.com/platform/bootable/recovery/+/25a5e7441981efd5a2d174a060d5d5fa031e1ffe/install/wipe_data.cpp#109).

`metadata` is useful preservation and diagnostic material, **not an instruction to restore it unchanged in a clean-reset workflow**. It can contain snapshot state and protected userdata encryption key blobs. Without the old userdata, restoring those blobs does not recreate the former user environment; a later clean recovery must deliberately establish consistent data/encryption and snapshot state. Keep this file private despite omitting personal files. [AOSP metadata encryption](https://source.android.com/docs/security/features/encryption/metadata#set-up-metadata-filesystem).

## Pending Virtual A/B snapshots

**Fact:** this saved Android inventory has `odm_a-cow`, `product_a-cow`, and `system_a-cow` mappings. Snapshot status commands were unavailable/inaccessible; a mapping name does not establish merge state or backing location. Virtual A/B puts changed firmware in COW snapshots, then merges it into base partitions. [Saved device inventory](device-inventory-2026-11-11.json); [AOSP Virtual A/B overview](https://source.android.com/docs/core/ota/virtual_ab).

**Fact:** COW storage can combine free space in `super` with backing images in data storage. AOSP's mapper handles a COW partition, COW file, or their concatenation. Therefore raw `super` plus `metadata` is not inherently self-contained when `userdata` is omitted. [AOSP snapshot mapping/allocation source](https://android.googlesource.com/platform/system/core/+/2ac86de15a33877b301500c211b49990ec76e8e8/fs_mgr/libsnapshot/snapshot.cpp#1428); [AOSP data-space implementation requirement](https://source.android.com/docs/core/ota/virtual_ab/implement#reduce-storage-requirements).

**Consequence:** if required COW firmware blocks reside in omitted userdata, factory reset cannot recover those blocks. A partly merged base may also be unsuitable as either a complete old build or a complete new build. AOSP's protections block one-off userdata/metadata wipes in `SNAPSHOTTED`/`MERGING` and slot changes in `MERGING`; do not defeat those protections to simplify a backup. [AOSP fastboot snapshot protections](https://source.android.com/docs/core/ota/virtual_ab/implement#fastboot-tooling-changes). Older AOSP recovery snapshot code also explicitly treats an unverified update differently from a merging one and can invalidate the target slot; these are reference semantics, not a verified match for BOOX's vendor binaries. [AOSP recovery snapshot handling](https://android.googlesource.com/platform/system/core/+/2ac86de15a33877b301500c211b49990ec76e8e8/fs_mgr/libsnapshot/snapshot.cpp#2161).

Offline inspection of saved `metadata`, `misc`, and `super` should establish snapshot state and any COW-file sizes/backing dependencies. If it proves no omitted firmware dependency and the partition/AVB checks pass, the raw set becomes a stronger candidate. Unreadable state, a missing tool, or an empty property is **unknown**, not evidence that snapshots are absent. If userdata-backed COW exists, retain the set as useful boot-chain/configuration preservation; do not claim exact raw-state recovery.

The verified matching OTA offers a separate **plausible clean reconstruction route**: its 13 full images include all five logical firmware images (`odm`, `product`, `system`, `system_ext`, `vendor`). AOSP defines full updates as final-image assets; the local validation establishes which images this BOOX package actually includes. A future offline plan can build a consistent snapshot-free `super` layout, pair it with matching boot/AVB assets and retained own-device state, and specify appropriate reset/snapshot handling. This requires layout/extent, image hash, AVB-chain, and rollback review; it is not accomplished merely by saving the files, and OTA acceptance or a successful restore is not proven. [Local validation](stock-firmware-validation-2026-11-11.json); [AOSP full OTA definition](https://source.android.com/docs/core/ota/tools#build-full-updates); [AOSP dynamic partition layout](https://source.android.com/docs/core/ota/dynamic_partitions/implement); [AOSP AVB verification and rollback model](https://android.googlesource.com/platform/external/avb/+/refs/heads/main/README.md).

## eMMC hardware boot areas and RPMB

The reported four physical areas are **consistent with** main user area, two hardware boot areas, and RPMB. They do not prove this programmer's numbering, capacities, or supported read behavior. The GPT's `boot_a/b` and `xbl_a/b` are partitions **inside LUN0**, separate from eMMC hardware `boot0/boot1`. Linux documents the latter as separate devices that can hold boot-critical configuration. [Linux MMC boot partition documentation](https://docs.kernel.org/driver-api/mmc/mmc-dev-parts.html).

**Recommendation:** preserve both hardware boot areas if their mapping, sizes, and bounded non-writing reads can be qualified with the existing programmer. A LUN0 dump does not include them. If that qualification is unavailable, record their omission explicitly. Their absence need not prevent a useful LUN0 backup for narrowly scoped future system/ROM work that leaves them untouched, but the result is not a complete eMMC recovery image. Do not change eMMC boot selection, write protection, partition configuration, or fuse state to obtain a dump.

**Do not treat a presumed physical area 3 as an ordinary raw RPMB partition.** RPMB has authenticated protocol state and an increasing write counter; a copied data file cannot capture/rewind all of that state. AOSP also describes rollback-resistant keys backed by trusted state such as RPMB. This backup cannot guarantee reversal of later security/rollback transitions. [Arm platform security guide, RPMB model](https://documentation-service.arm.com/static/60ddc8bb0320e92fa40b5b96); [AOSP Keymaster rollback-resistant storage](https://android.googlesource.com/platform/docs/source.android.com/+/e55b3193405187e091a4ac7730ef04360ec04504/en/security/keystore/implementer-ref.html).

## Acceptance boundary

Record every captured and excluded extent, byte length and SHA-256; validate GPT and `super` metadata and independently reread critical small firmware/configuration areas. Keep two protected copies. **A successful read and useful recovery assets are distinct from a demonstrated restoration.** The backup-only scope does not authorize flashing, erase/reset, slot changes, snapshot cancellation/merge commands, or a ROM experiment. Snapshot completeness, hardware-area omissions, BOOX write/restore acceptance, and clean-reset boot remain explicit open items.
